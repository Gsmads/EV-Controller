# CLAUDE.md — правила проекта EV Controller

Этот файл читается в начале каждой сессии. Он описывает, как устроен проект,
что можно менять свободно, а что требует решения владельца.

---

## 1. Что это за проект

Прошивка контроллера **детского электромобиля** на Arduino Nano (ATmega328P, 16 МГц)
плюс веб-интерфейс для настройки и отладки с компьютера.

**В машине ездит ребёнок.** Это не учебный проект и не игрушечный стенд.
Любое изменение в цепочке «педаль → рампа → ШИМ → мотор», в тормозной логике,
в аварийной остановке или в watchdog — изменение, которое может привести к травме.
Такие правки не делаются походя (см. §5).

Полное ТЗ: `docs/EV_Controller_Specification.md`.

## 2. Текущее состояние — читать до первой правки

**Код никогда не исполнялся на реальном железе.** Ни одной проверки на контроллере
не было. Считай его подробным черновиком, а не работающей системой.

Обязательно прочитать перед работой:
- `docs/AUDIT.md` — технический аудит. Содержит 4 блокирующих дефекта,
  4 дефекта безопасности и план исправлений по очередям. Это карта того,
  что сломано и в каком порядке чинить.
- `docs/METHODOLOGY.md` — методология разработки владельца. Принципы оттуда —
  критерии приёмки, а не пожелания.

**Документация местами расходится с кодом.** На момент аудита:
- `docs/PROTOCOL.md` описывает протокол v1, в коде v2 — документ устарел целиком;
- `docs/ARCHITECTURE.md` не содержит слоистой модели педалей (главное решение v2);
- `docs/ARCHITECTURE.md` перечисляет задачу `wdt_reset`, которой в коде нет.

Правило на время расхождений: **истина — код, но расхождение чинится, а не
обходится.** Нашёл несоответствие — либо приведи документ в соответствие тем же
PR, либо зафиксируй в `docs/AUDIT.md`. Не оставляй молча.

## 3. Архитектура и границы

Четыре слоя, зависимости направлены **только вниз**:

```
Application   app_main (планировщик), app_protocol, app_debug
     ↓
Services      svc_pedals, svc_ramp, svc_motor, svc_speed
     ↓
Drivers       drv_* (пока пусто, появятся в MVP-3)
     ↓
HAL           hal_gpio, hal_adc, hal_pwm, hal_uart, hal_eeprom,
              hal_encoder, hal_system, hal_spi, hal_i2c
     ↓
Hardware      ATmega328P
```

Cross-cutting (доступны с любого слоя): `cfg_board.h`, `cfg_settings`, `util_math`, `util_crc`.

### Нерушимые правила

1. **`Arduino.h`, `avr/io.h`, `avr/interrupt.h` разрешены ТОЛЬКО в `hal_atmega328p.cpp`.**
   Ни один файл `svc_*`, `util_*`, `cfg_settings*`, `app_*` не имеет права их включать.
   Это то, что делает проект переносимым. Проверяется CI-сторожем.
2. **Слой не вызывает слой выше.** HAL не знает о сервисах, сервисы не знают о `app_*`.
3. **Горизонтально — только через публичный интерфейс.** `svc_motor` вызывает
   функции `svc_ramp`, но не лезет в его статические переменные.
4. **`delay()` запрещён везде.** Блокировка ломает цикл управления 100 Гц.
   `hal_system_delay_us()` — только внутри HAL для аппаратных протоколов (HX711).
5. **Никакой динамической памяти.** Ни `malloc`, ни `new`, ни `String`, ни VLA.
   2 КБ RAM, фрагментация недопустима.
6. **Только целочисленная арифметика в сервисах.** Fixed-point (×100 для PID,
   ×256 для EMA). `float` допустим лишь там, где уже используется (`printFloat`).

### Соглашения об именовании

```
Файлы:      hal_*  drv_*  svc_*  app_*  cfg_*  util_*
Функции:    <модуль>_<глагол>()      svc_ramp_update(), hal_adc_read()
Типы:       <модуль>_state_t, <модуль>_config_t, <модуль>_id_t
Константы:  <МОДУЛЬ>_<ИМЯ>
```

Идентификаторы — английские. **Комментарии и документация — русские.**
Каждый публичный прототип снабжён doxygen-блоком: назначение, параметры,
возвращаемое значение, частота вызова (если модуль вызывается планировщиком).

## 4. Сборка, тесты, проверки

```bash
cd tests && make run       # 71 тест, ~5 секунд, должно быть 0 failed
cd tests && make clean     # убрать бинарники перед коммитом
```

Прошивка собирается Arduino IDE из папки `firmware/` (плоская структура —
требование IDE). Все `.cpp` в корне скетча компилируются автоматически.

Веб:
```bash
cd tools/gui && pip install -r requirements.txt && python server.py
# http://localhost:8000
```

### Требования к тестам

- **Любое изменение в `util_*`, `cfg_*`, `svc_*` сопровождается тестом.**
  Эти модули платформонезависимы и тестируются на десктопе через `g++`.
- **Исправление дефекта начинается с теста, который его воспроизводит.**
  Сначала красный тест, потом правка, потом зелёный.
- Для формул (скорость, частота ШИМ, кривые) — **эталонные точки с
  посчитанным вручную ожидаемым значением**, а не «выглядит правдоподобно».
  В аудите есть пример, к чему приводит комментарий-самоподтверждение.
- HAL тестируется только на железе. Для сервисов пишутся моки HAL-функций
  в тестовом файле (пример: `tests/test_cfg_settings.c`, мок EEPROM).

## 5. Что требует решения владельца

Владелец решает, ассистент предлагает. По этим темам **не действуй сам** —
оформи развилку: варианты таблицей «что делает / чем платим», с рекомендацией,
и дождись ответа.

- изменение поведения педалей, тормоза, рампы, аварийной остановки;
- изменение watchdog (любого из трёх: аппаратного, UART-связи, UART-педалей);
- изменение бинарного протокола: команды, формат телеметрии, версия;
- изменение структуры `settings_t` и раскладки EEPROM;
- новые внешние зависимости (Arduino-библиотеки, Python-пакеты, JS-библиотеки) —
  с указанием зачем, лицензия, вес, альтернативы;
- смена частоты UART, частот ШИМ, назначения таймеров и пинов;
- всё, что меняет обещание пользователю, данное в ТЗ.

Решения владельца оформляются как ADR в `docs/adr/` (контекст, решение,
последствия, **отклонённые варианты с причинами**). Отклонённый вариант,
записанный с причиной, экономит следующему кругу разговора.

## 6. Definition of Done

Задача закрыта, когда выполнено **всё**:

1. Критерий приёмки сформулирован **наблюдаемым поведением**, не «код написан».
   Плохо: «добавлен watchdog». Хорошо: «при зависании основного цикла контроллер
   перезагружается за 8 секунд, ШИМ обнуляется, это видно на осциллографе».
2. Тест, воспроизводящий проблему, был красным и стал зелёным.
3. `cd tests && make run` — 0 failed.
4. Затронутая документация обновлена тем же изменением.
5. Если решение было неочевидным — записан ADR.

## 7. Стиль работы

- **Мелкими шагами.** Один дефект — одно изменение — один коммит.
  Не чини попутно то, о чём не просили: заметил — запиши в `docs/AUDIT.md`
  или скажи, но не смешивай с текущей задачей.
- **Не изобретай молчаливых заглушек.** Если значение неизвестно (нет датчика,
  не реализовано), это отдельное состояние с именем, а не `0`. Сейчас в коде
  `faults = 0` и `drive_mode = ECO` выдаются за данные — так делать больше нельзя.
- **Не отвечай ACK на невыполненное действие.** Если команда не реализована —
  `NACK` с кодом «не реализовано», и веб это показывает.
- **Сомневаешься в физике или формуле — посчитай.** Запусти расчёт, сверь
  с ручным вычислением, приложи числа к объяснению.
- Не добавляй эмодзи в код и коммиты.

## 8. Незакрытые вопросы

Эти параметры **выдуманы** и должны быть уточнены владельцем на железе.
Пока они неизвестны, зависящие от них функции считаются непроверенными:

| Параметр | Где | Текущее | Как получить |
|---|---|---|---|
| `ENCODER_PULSES_PER_REV` | `cfg_board.h` | 12 | прокрутить колесо ровно на оборот, посчитать импульсы |
| `WHEEL_DIAMETER_MM` | `cfg_board.h` | 200 | замерить |
| `pedal_gas_min/max` | дефолты `cfg_settings.cpp` | 10 / 1000 | замерить АЦП в крайних положениях |
| `motor_deadzone` | дефолты | 30 | найти минимальный ШИМ, при котором колесо трогается |
| скорость UART | `cfg_board.h` | 9600 | ТЗ §7.1 предполагает 115200 — решение владельца |
| загрузчик Nano | — | неизвестен | от этого зависит, безопасно ли включать watchdog |
