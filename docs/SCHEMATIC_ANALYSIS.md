# Анализ схемы контроллера TED CAR_DRIVER

**Дата анализа:** 2026-05-11  
**Версия схемы:** V1.0  
**Листы:** 6 страниц (MCU, RS485_L1, Isol_IN_OUT, Analog_input, Relay, IN_OUT)

---

## 1. Общая архитектура — что сделано правильно

### 1.1 Полная гальваническая изоляция силовой части

Все сигналы между MCU (Arduino Nano) и силовыми драйверами проходят через оптопары **8N137-X009T**. Это высокоскоростные оптопары (до 10 Мбит/с), что позволяет передавать PWM-сигналы без существенных потерь. Изолированы:
- PWM правого мотора (PWM_R → PWM_R_OUT)
- PWM левого мотора (PWM_L → PWM_L_OUT)
- PWM рулевого усилителя (PWM_V → PWM_V_OUT)
- SPI-шина к HC595 (MOSI, SCK, CS)
- Обратные сигналы скорости колёс (SPEEDPULSEOUT_R/L)

**Это отличное решение** для автомобиля с мощными DC-моторами, которые генерируют сильные EMI-помехи.

### 1.2 RS485 с гальванической изоляцией и PoE

Интерфейс RS485 (ADM3491ARZ) имеет:
- Изолированное питание через DC-DC конвертер **B1205S-1WR3** (1 Вт)
- ESD-защиту CDSOT23-SRV05-4 на линиях данных
- Polyfuses (MF-MSMF020-2) для защиты от перегрузки по току
- PoE-подобную подачу питания через тот же RJ45-кабель с мостовыми выпрямителями (SS24) для полярно-независимого подключения
- LED-индикаторы состояния линий

### 1.3 Аппаратный watchdog на реле (NE555)

Схема реле (стр. 5) реализует **аппаратный таймер безопасности**:
- Реле силового питания моторов (RL1, RL2, RL3) управляются через NE555 в моностабильном режиме
- NE555 требует периодического перезапуска от MCU
- При зависании MCU или потере I2C-связи с PCA9535 → таймер NE555 истекает → реле обесточиваются → моторы теряют питание
- Это **аппаратный уровень безопасности**, независимый от программы

### 1.4 Кондиционирование аналоговых входов

Все аналоговые сигналы проходят через:
- RC-фильтры (1 кОм + 100 пФ + 510 кОм)
- ESD-защиту BAT54SQ-13 (клампирование к +5V и AGND)
- Буферные ОУ LM224D
- Разделённую аналоговую землю (AGND) через R70=0Ω (star ground)

### 1.5 Входные сигналы через триггеры Шмитта

Дискретные входы (кнопки, переключатели) проходят через **SN74HC14DR** — обеспечивая чистые фронты, гистерезис (антидребезг) и согласование уровней 3.3V→5V.

## 2. КРИТИЧЕСКИЕ расхождения между схемой и ТЗ

### 2.1 ⚠️ Отсутствует HX711 — усилие на руле измеряется аналогово

| Параметр | ТЗ (Specification) | Схема (Schematic) |
|----------|--------------------|--------------------|
| Датчик усилия на руле | HX711 (24-бит, D5=DOUT, D12=SCK) | Аналоговый через ОУ LM224D → A3 |
| Разрешение | 24 бита | 10 бит (ADC Arduino) |
| Занятые пины | D5, D12 | A3 (аналоговый) |

**Влияние на прошивку:**
- НЕ нужна библиотека HX711
- Усилие читается стандартным `analogRead(A3)`
- Разрешение значительно ниже (1024 уровня vs 16 млн), но для EPS детского автомобиля 10 бит вполне достаточно
- Пины D5 и D12 освобождены для других функций

### 2.2 ⚠️ Изменена распиновка Arduino Nano

| Пин | ТЗ | Схема | Комментарий |
|-----|-----|-------|-------------|
| D5 | HX711 DOUT | **PWM_V** (EPS PWM) | HX711 убран, D5 используется как OC0B (Timer0) |
| D6 | PWM EPS (OC0A) | **INTC1** (прерывание PCA9535) | Сдвиг на 1 пин вниз |
| D7 | INT PCA9535 | **CS_SPI** (Latch HC595) | Сдвиг на 1 пин вниз |
| D8 | CS HC595 | *Свободен?* | Нужно уточнить |
| D12 | HX711 SCK | *Не используется / MISO?* | HX711 убран |
| A3 | Положение руля (Холл) | **VICHINEFORCE** (усилие) | Конфликт назначения! |

**⚡ КРИТИЧНО:** В ТЗ A3 = положение руля (датчик Холла), а в схеме A3 = усилие на руле (VICHINEFORCE). **Где подключён датчик положения руля?** Это нужно уточнить, потому что PID-регулятор EPS требует ОБА сигнала: и положение, и усилие.

### 2.3 ⚠️ Третий датчик тока (CURRMETER3)

Схема показывает **три** канала измерения тока (CURRMETER1, CURRMETER2, CURRMETER3), а ТЗ предусматривает только два (правый и левый мотор). Третий, вероятно, для мотора EPS. Это полезно, но нужно определить, к какому аналоговому пину MCU он подключён.

### 2.4 ⚠️ Маркировка A8 на аналоговой плате

На странице Analog_input выход ОУ для ACCELERATOR помечен как **A8**. Arduino Nano имеет только A0–A7. Это ошибка маркировки — скорее всего, должно быть A0 (педаль газа).

## 3. Нюансы, важные для прошивки

### 3.1 Инверсия сигналов через оптопары

**8N137-X009T инвертирует сигнал:** вход HIGH → LED ON → выход LOW.

Это означает:
- PWM с MCU инвертируется на изолированной стороне
- SPI-данные инвертируются
- Сигналы скорости колёс инвертируются

**Для PWM:** Если ZS-X11H ожидает active-HIGH PWM, то:
```
// Вместо:
analogWrite(PWM_PIN, speed);    // 0=стоп, 1023=макс
// Нужно:
analogWrite(PWM_PIN, 1023 - speed);  // инвертированный PWM
```

**Для SPI (HC595):** данные, тактовый сигнал и latch инвертированы. HC595 может работать с инвертированными фронтами, но нужно проверить полярность на осциллографе. Возможно потребуется программная инверсия битов:
```
shiftOut(MOSI, SCK, MSBFIRST, ~data);  // инверсия всех бит
```

**Рекомендация:** Определить константы полярности в конфигурации:
```cpp
#define PWM_INVERT      true   // true если оптопара инвертирует
#define SPI_DATA_INVERT true
#define SPEED_PULSE_ACTIVE_LOW true
```

### 3.2 Timer0 конфликт (PWM EPS на D5/OC0B)

PWM для EPS теперь на **D5 (OC0B, Timer0)**. Timer0 используется ядром Arduino для:
- `millis()`
- `micros()`
- `delay()`

**Изменение частоты или режима Timer0 сломает эти функции!**

Решения:
1. **Использовать Timer0 "как есть"** — стандартная частота PWM ~976 Гц на D5/D6 (phase-correct, prescaler 64). Для EPS это может быть достаточно, но шум мотора будет слышен.
2. **Переконфигурировать Timer0** и реализовать собственный счётчик времени на Timer2 или через ISR.
3. **Рассмотреть перенос EPS PWM на D3 (OC2B, Timer2)** — если пин D3 можно перемаршрутизировать. Но D3 занят прерыванием энкодера.

**Рекомендация для MVP:** оставить Timer0 в стандартном режиме, ~976 Гц PWM на D5 для EPS. Позже оптимизировать.

### 3.3 Маппинг битов HC595 — необходимо верифицировать

Из схемы Isol_IN_OUT видно, что 74HC595 (U16) управляет сигналами двух моторных драйверов и рулевого драйвера BTS7960:

**Предположительный маппинг (из разводки платы):**

| Бит Q | Сигнал | Описание |
|-------|--------|----------|
| Q0 | DIR_R | Направление правого мотора |
| Q1 | STOP_R | Остановка правого мотора |
| Q2 | BRAKE_R | Тормоз правого мотора |
| Q3 | DIR_L | Направление левого мотора |
| Q4 | STOP_L | Остановка левого мотора |
| Q5 | BRAKE_L | Тормоз левого мотора |
| Q6 | V_L | BTS7960 L_EN (поворот влево) |
| Q7 | V_R | BTS7960 R_EN (поворот вправо) |

**⚠️ Этот маппинг ОТЛИЧАЕТСЯ от ТЗ!** В ТЗ:
- Q0 = R_EN (поворот вправо), Q7 = L_EN (поворот влево)
- Q1 = DIR правого, Q2 = STOP правого, Q3 = BRAKE правого
- Q4 = DIR левого, Q5 = STOP левого, Q6 = BRAKE левого

**Маппинг ОБЯЗАТЕЛЬНО** верифицировать прозвонкой PCB перед написанием финального кода. Определить как `#define` для лёгкой коррекции:

```cpp
// HC595 bit mapping — VERIFY ON ACTUAL PCB!
#define HC595_DIR_R    (1 << 0)
#define HC595_STOP_R   (1 << 1)
#define HC595_BRAKE_R  (1 << 2)
#define HC595_DIR_L    (1 << 3)
#define HC595_STOP_L   (1 << 4)
#define HC595_BRAKE_L  (1 << 5)
#define HC595_V_L      (1 << 6)  // BTS7960 L_EN
#define HC595_V_R      (1 << 7)  // BTS7960 R_EN
```

### 3.4 PCA9535 — адрес I2C и конфигурация портов

Из схемы IN_OUT:
- **Адресные пины A0, A1, A2** подключены к GND → **I2C-адрес = 0x20**
- **Прерывание INT#** → INTC1 → D6 Arduino (или D7 по ТЗ)

Конфигурация портов:
```
Port 0 (IO0_0..IO0_7) = ВЫХОДЫ:
  SW0_1..SW0_3 → доп. управление (фары fallback?)
  SW0_4..SW0_5 → резерв
  SW0_6       → Реле EPS (RL1)
  SW0_7       → Реле правого мотора (RL2)
  SW0_8       → Реле левого мотора (RL3)

Port 1 (IO1_0..IO1_7) = ВХОДЫ:
  SW1_1       → Кнопка зажигания
  SW1_2       → Нейтраль
  SW1_3       → Ручник
  SW1_4       → Forward Mode 1 (Eco)
  SW1_5       → Forward Mode 2 (Sport)
  SW1_6       → Reverse
  SW1_7..SW1_8 → Резерв
```

**Инициализация PCA9535:**
```cpp
// Регистры PCA9535
#define PCA9535_ADDR         0x20
#define PCA9535_INPUT_PORT0  0x00
#define PCA9535_INPUT_PORT1  0x01
#define PCA9535_OUTPUT_PORT0 0x02
#define PCA9535_OUTPUT_PORT1 0x03
#define PCA9535_CONFIG_PORT0 0x06  // 0=output, 1=input
#define PCA9535_CONFIG_PORT1 0x07

// Init:
// Port 0 = all outputs (0x00)
// Port 1 = all inputs  (0xFF)
Wire.beginTransmission(PCA9535_ADDR);
Wire.write(PCA9535_CONFIG_PORT0);
Wire.write(0x00);  // Port 0 = outputs
Wire.endTransmission();

Wire.beginTransmission(PCA9535_ADDR);
Wire.write(PCA9535_CONFIG_PORT1);
Wire.write(0xFF);  // Port 1 = inputs
Wire.endTransmission();
```

### 3.5 Инверсия входных сигналов через SN74HC14

Триггеры Шмитта **SN74HC14DR инвертируют сигнал**. Кнопки с подтяжкой к +3.3V (через разъёмы J1, J2):
- Кнопка НЕ нажата → вход HIGH → Шмитт → выход LOW → PCA9535 Port 1 читает 0
- Кнопка нажата → вход LOW → Шмитт → выход HIGH → PCA9535 Port 1 читает 1

Итого: **в прошивке значение 1 = кнопка нажата, 0 = отпущена** (после двойной инверсии Шмитта восстанавливается прямая логика, ЕСЛИ кнопки замыкают на GND; если на +3.3V — то инвертировано).

**Нужно уточнить схему подключения кнопок** (pull-up + замыкание на GND или pull-down + замыкание на VCC).

### 3.6 Управление реле — протокол перезапуска NE555

Реле управляются через PCA9535 → NE555 → IRFL024NPBF → реле.

**Логика работы:**
1. PCA9535 выставляет SW0_6/7/8 = HIGH
2. Сигнал через 2N7002 MOSFET подаёт LOW-импульс на TRIGGER NE555
3. NE555 активирует IRFL024NPBF на время таймаута (t = 1.1 × R × C)
4. Реле включается
5. При удержании входа HIGH → NE555 удерживает выход

**Для прошивки:**
```cpp
// Включение силового питания моторов
void enableMotorPower(bool right, bool left, bool eps) {
    uint8_t relay_bits = 0;
    if (eps)   relay_bits |= (1 << 5);  // SW0_6 = RL1 (EPS)
    if (right) relay_bits |= (1 << 6);  // SW0_7 = RL2 (Right motor)
    if (left)  relay_bits |= (1 << 7);  // SW0_8 = RL3 (Left motor)
    
    pca9535_writePort0(relay_bits);
}
```

### 3.7 Передаточная функция аналоговых входов

Все каналы ОУ (LM224D) имеют одинаковую схему усиления:

**Формула: V_out = 1.1 × V_in − 0.5V**

(R_feedback = 100Ω, R_to_5V = 1kΩ)

**Обратная формула для прошивки:**
```cpp
// Преобразование ADC-значения в реальное напряжение на датчике
float adcToSensorVoltage(uint16_t adc_raw) {
    float v_out = (float)adc_raw * 5.0f / 1023.0f;  // Напряжение на выходе ОУ
    float v_sensor = (v_out + 0.5f) / 1.1f;          // Напряжение на входе датчика
    return v_sensor;
}

// Для ACS712-20A (чувствительность 100 мВ/А, ноль при 2.5В):
float adcToCurrent(uint16_t adc_raw) {
    float v_sensor = adcToSensorVoltage(adc_raw);
    return (v_sensor - 2.5f) / 0.1f;  // Ток в амперах
}

// Для педали (0–5V → 0–100%):
float adcToPedalPercent(uint16_t adc_raw) {
    float v_sensor = adcToSensorVoltage(adc_raw);
    return constrain(v_sensor / 5.0f * 100.0f, 0.0f, 100.0f);
}
```

### 3.8 RS485 — управление направлением передачи

Из схемы RS485_L1:
- **DE и RE# ADM3491** управляются сигналом **L1_CS** (через буфер SN74HC125)
- L1_CS = HIGH → передача (DE=1, RE#=1)
- L1_CS = LOW → приём (DE=0, RE#=0)
- L1_CS идёт от пина **RS485_ON** (D4) через изоляцию

```cpp
#define RS485_DE_PIN 4  // D4 = RS485 direction control

void rs485_transmit_mode() {
    digitalWrite(RS485_DE_PIN, HIGH);
    delayMicroseconds(5);  // Время переключения трансивера
}

void rs485_receive_mode() {
    digitalWrite(RS485_DE_PIN, LOW);
    delayMicroseconds(5);
}
```

**Важно:** ТЗ указывает 115200 бод, но текущий MICRO_UART.h задаёт `#define BAUD_RATE 9600`. Нужно обновить до 115200.

### 3.9 Ограничение мощности B1205S-1WR3

Изолированный DC-DC конвертер B1205S-1WR3 имеет мощность **1 Вт** (выход: 5V / 200 мА). Потребители на изолированной стороне RS485:
- ADM3491ARZ: ~50 мА
- SN74HC125: ~10 мА
- LED-индикаторы: ~30 мА
- Запас: ~110 мА

Запас достаточен, но при добавлении дополнительных устройств на шину RS485 нужно контролировать потребление.

## 4. Потенциальные проблемы и рекомендации

### 4.1 ❌ Отсутствует RS485 терминация

На схеме RS485 видны R1=10k и R11=10k — это bias-резисторы, **НЕ терминация**. Стандартная RS485 терминация — **120Ω** между A и B на конце линии.

Для коротких кабелей в детском автомобиле (< 2м) это может работать, но при EMI от моторов рекомендуется добавить терминационный резистор 120Ω. Возможно, его можно подключать через DIP-switch SW1 (CAS-220TB), который виден на схеме.

### 4.2 ⚠️ LM224D — не rail-to-rail, ограничение выходного диапазона

LM224D не является rail-to-rail ОУ:
- Минимальный выход: ~20 мВ (при питании от +5V и GND)
- Максимальный выход: ~3.5V при нагрузке (типично V_sat ≈ 1.5V от VCC)

Это ограничивает диапазон ADC:
- При V_in = 0V → V_out = 1.1×0 − 0.5 = −0.5V → клиппинг на ~0V → ADC ≈ 0
- При V_in = 5V → V_out = 1.1×5 − 0.5 = 5.0V → клиппинг на ~3.5V → ADC ≈ 716

**Эффективный диапазон ADC: ~0–716 из 1023.** Это снижает разрешение на ~30%.

**Рекомендация:** Для будущей ревизии заменить LM224D на rail-to-rail ОУ (например, MCP6004, LMV324).

### 4.3 ⚠️ Нет pull-down на затворах IRFL024NPBF при сбросе NE555

Если NE555 находится в состоянии сброса (power-on), его выход — LOW. Но при переходных процессах (включение питания) состояние выхода может быть неопределённым.

Резисторы R89/R90/R101 = 9.1k обеспечивают pull-down на затворах IRFL024NPBF — это хорошо. Реле будут ВЫКЛЮЧЕНЫ при неопределённом состоянии NE555.

### 4.4 ⚠️ Совместимость уровней 3.3V ↔ 5V

Из блок-диаграммы: связь Arduino ↔ ESP32 через конвертер уровней (3.3V↔5V). Это правильно.

Но на странице IN_OUT: внешние входы через разъёмы J1, J2 помечены **+3.3V** (SELV1, SELV2). Если эти входы идут от 3.3V-датчиков, а SN74HC14 питается от 5V:
- Порог переключения SN74HC14 при VCC=5V: ~2.5V (типично)
- 3.3V HIGH сигнал > 2.5V порога → детектируется как HIGH ✓
- Но запас (3.3V − 2.5V = 0.8V) невелик. При помехах возможны ложные срабатывания.

**Рекомендация:** Для 3.3V-входов рассмотреть SN74LVC14 (VCC=3.3V) или снижение порога через делитель.

### 4.5 ⚠️ Конденсаторы развязки оптопар

На странице Isol_IN_OUT каждый оптрон имеет конденсатор 0.1 мкФ (C12, C14, C17, etc.) на выходе. Это хорошо для фильтрации ВЧ-помех, но может ограничить скорость нарастания фронтов PWM-сигнала.

Для PWM 8–16 кГц с 10-битным разрешением минимальный период = 1/16000 = 62.5 мкс. При 10-битном разрешении каждый шаг = ~61 нс. RC-фильтр (10k pull-up + 100nF) даёт τ = 1 мс — это **СЛИШКОМ медленно** для PWM!

**Нужно проверить:** величины pull-up резисторов на выходах оптопар. Если pull-up = 10k, а cap = 100nF → τ = 1 мс → ограничение до ~1 кГц PWM. Для 8+ кГц нужен pull-up ≤ 1k или убрать конденсатор на PWM-линиях.

Из схемы видно, что некоторые pull-up — R7=10k (MOSI_ISO), R17=? Нужно уточнить для PWM-линий.

### 4.6 Скорость SPI к HC595 через оптопары

SPI-сигналы (MOSI, SCK, CS) проходят через оптопары. При pull-up 1k и ёмкости 100pF паразитной:
- τ ≈ 1k × 100pF = 100 нс
- Максимальная частота SPI ≈ 1/(4 × 100 нс) ≈ 2.5 МГц

Arduino SPI по умолчанию работает на F_CPU/4 = 4 МГц. **Может потребоваться снижение скорости SPI до 2 МГц или ниже.**

```cpp
SPI.beginTransaction(SPISettings(2000000, MSBFIRST, SPI_MODE0));
```

## 6. Рекомендации перед началом разработки прошивки

### 6.1 Обязательно перед написанием кода:

1. **Прозвонить PCB** — верифицировать маппинг битов HC595 к сигналам DIR/STOP/BRAKE/V_L/V_R
2. **Измерить осциллографом** задержку оптопар на PWM-линиях с реальной нагрузкой
3. **Проверить полярность оптопар** — инвертирующий или неинвертирующий выход 8N137
4. **Уточнить подключение аналоговых входов** — какой датчик на каком пине Arduino
5. **Уточнить положение датчика Холла руля** — на каком пине он в реальности
6. **Проверить время таймаута NE555** — измерить RC-параметры для определения частоты перезапуска реле
7. **Проверить pull-up на PWM-выходах оптопар** — если >1k, заменить для поддержки 8+ кГц PWM

### 6.2 Архитектура прошивки — модули

На основании анализа схемы, рекомендую следующую модульную структуру:

```
Модули прошивки:
├── HAL (Hardware Abstraction Layer)
│   ├── hal_pins.h          — все #define пинов (по СХЕМЕ, не по ТЗ!)
│   ├── hal_timer.cpp/h     — Timer1 (PWM моторов), Timer0 (PWM EPS)
│   ├── hal_spi.cpp/h       — SPI с учётом инверсии оптопар
│   ├── hal_i2c.cpp/h       — I2C для PCA9535
│   ├── hal_adc.cpp/h       — ADC с передаточной функцией ОУ
│   └── hal_uart.cpp/h      — RS485 UART (обновить до 115200!)
├── Drivers
│   ├── drv_hc595.cpp/h     — управление сдвиговым регистром
│   ├── drv_pca9535.cpp/h   — расширитель портов I2C
│   ├── drv_motor.cpp/h     — управление ZS-X11H (DIR/STOP/BRAKE/PWM)
│   ├── drv_eps.cpp/h       — управление BTS7960 (EPS)
│   └── drv_relay.cpp/h     — управление силовыми реле через NE555
├── Control
│   ├── ctrl_pedals.cpp/h   — обработка педалей газа/тормоза
│   ├── ctrl_steering.cpp/h — PID-регулятор EPS
│   ├── ctrl_modes.cpp/h    — режимы вождения (Eco/Normal/Sport)

│   ├── proto_rs485.cpp/h   — протокол RS485 (команды + телеметрия)
│   └── proto_crc16.cpp/h   — CRC16 для пакетов
└── main.cpp
```

## 7. Итоги

### Что сделано отлично:
- Полная гальваническая изоляция силовой части
- RS485 с изоляцией и PoE — промышленный уровень
- Аппаратный watchdog на реле (NE555)
- ESD-защита на всех внешних линиях
- Кондиционирование аналоговых входов с фильтрацией
- Триггеры Шмитта на дискретных входах
- LED-индикация состояний

### Что требует внимания:
- Расхождение распиновки между ТЗ и схемой (особенно A3, D5–D8)
- Инверсия сигналов через оптопары — нужна верификация
- RC-постоянная на PWM-линиях может ограничить частоту
- LM224D не rail-to-rail — ограничение динамического диапазона ADC
- Отсутствие терминации 120Ω на RS485
- Скорость UART в коде (9600 vs требуемые 115200)
