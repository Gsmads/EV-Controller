# Правила ведения проекта

**Версия:** 1.0 · 09.09.2026
**Опирается на:** `METHODOLOGY.md`, `ARCHITECTURE.md`

Этот документ описывает, как в проекте пишется код, документируются решения
и ведётся работа. Он обязателен и для человека, и для ассистента.

---

## 1. Границы, которые не пересекаются

1. **Платформозависимый код — только в `hal_<platform>.cpp`.**
   `Arduino.h`, `avr/io.h`, `avr/interrupt.h`, `avr/eeprom.h`, `avr/wdt.h`
   не имеют права появиться ни в одном файле `svc_*`, `util_*`, `cfg_*`,
   `app_*`, `drv_*`. Проверяется сторожем в CI.

2. **Функции Arduino не используются нигде, включая HAL.**
   `digitalWrite`, `digitalRead`, `pinMode`, `analogRead`, `analogWrite`,
   `millis`, `micros`, `delay`, `delayMicroseconds`, `shiftOut`, `Serial`,
   `Wire`, `SPI` заменяются собственными реализациями на регистрах.
   Причины: переносимость, предсказуемое время выполнения, отсутствие
   скрытых зависимостей от ядра. Исключение возможно только с ADR.

3. **Зависимости направлены вниз.**
   `app_* → svc_* → drv_* → hal_*`. Обратных вызовов нет. Горизонтально —
   только через публичный интерфейс модуля, не через его внутренние данные.

4. **`delay()` запрещён.** Блокировка ломает цикл управления.
   `hal_delay_us()` допустим внутри HAL для аппаратных протоколов
   (HX711, программный I²C), больше нигде.

5. **Динамическая память запрещена.** Ни `malloc`, ни `new`, ни `String`,
   ни массивы переменной длины. 2 КБ ОЗУ, фрагментация недопустима.

6. **Только целочисленная арифметика в сервисах.** Fixed-point:
   ×100 для коэффициентов PID, ×256 для фильтров. `float` — только там,
   где уже используется в унаследованном коде.

## 3. Комментирование

Цель — чтобы человек, открывший файл впервые, понял назначение модуля
за минуту, а назначение функции — не читая её тела.

### Шапка файла

```c
/**
 * @file svc_ramp.cpp
 * @brief Генератор рампы разгона и торможения
 *
 * Что делает: плавно изменяет ШИМ от текущего значения к целевому
 * с темпом, заданным профилем режима движения.
 *
 * Зачем: резкое изменение ШИМ даёт рывок, опасный для ребёнка
 * и вредный для редуктора.
 *
 * Где используется: вызывается из app_main с частотой 100 Гц,
 * между svc_pedals (источник цели) и svc_motor (потребитель результата).
 *
 * Чего НЕ делает: не знает про моторы, педали и режимы; получает
 * все параметры аргументами.
 */
```

### Прототип функции

Каждая публичная функция в заголовке снабжается блоком:

```c
/**
 * @brief Один шаг рампы
 *
 * @param target_pwm   Целевое значение ШИМ, 0..1023
 * @param brake_value  Педаль тормоза, 0..1023. Ненулевое значение
 *                     переопределяет target_pwm и ведёт ШИМ к нулю
 * @param profile      Профиль режима: темпы разгона и торможения
 *
 * @return Новое значение ШИМ, 0..1023
 *
 * @note Вызывать строго с частотой, переданной в svc_ramp_init().
 *       Отклонение частоты искажает фактический темп.
 * @warning Не вызывать из прерывания: функция не реентерабельна.
 */
uint16_t svc_ramp_update(uint16_t target_pwm, uint16_t brake_value,
                         const drive_profile_t *profile);
```

Обязательны: назначение, каждый параметр с диапазоном, возвращаемое значение,
частота вызова для периодических функций, ограничения.

### Внутри тела

Комментировать **почему**, а не **что**. Строка `i++; // увеличиваем i`
бесполезна. Строка `// накапливаем дробный остаток, иначе rate=150 при
100 Гц даст 1, а не 1.5` — полезна.

Формулы и магические числа сопровождаются выводом:

```c
/* v[км/ч] = RPM · π · D[мм] · 60 / 10⁶
 * kmh_x10 = RPM · D · 1885 / 10⁶
 * Проверка: RPM=300, D=255 → 300·255·1885/1e6 = 144 → 14.4 км/ч */
```

**Проверку в комментарии обязательно пересчитать перед тем, как писать.**
В истории проекта был случай, когда «проверка» подтверждала неверную
формулу, и ошибка в 3,6 раза прожила до аудита.

### Чего в комментариях быть не должно

- закомментированный код — для этого есть история git;
- `// TODO` без номера задачи — заводится issue, ссылка ставится в комментарий;
- обещания того, чего в коде нет.

## 4. Архитектурные решения (ADR)

Любое решение, которое дороже отменить, чем принять, записывается как ADR
в `docs/adr/NNNN-краткое-название.md` по шаблону `0000-template.md`.

**Что обязательно попадает в ADR:**
- изменение поведения педалей, тормоза, рампы, аварийной остановки;
- изменение любого watchdog;
- изменение протокола: команды, формат телеметрии, версия;
- изменение структуры `settings_t` и раскладки EEPROM;
- новая внешняя зависимость;
- смена частоты UART, частот ШИМ, назначения таймеров и пинов;
- отступление от правил раздела 1.

**Структура:** контекст → решение → последствия → **отклонённые варианты
с причинами**. Последний раздел важнее остальных: он экономит следующему
кругу спор, который уже был.

ADR не редактируются после принятия. Изменение решения — новый ADR
со ссылкой «заменяет ADR-NNNN».

## 5. Задачи (issues)

Заводятся на всё, что не делается прямо сейчас. Метки:

| Метка | Значение |
|---|---|
| `blocker` | без этого нельзя включать железо |
| `safety` | касается безопасности ребёнка |
| `hw-unknown` | ждёт замера на стенде, см. `HARDWARE_BRINGUP.md` |
| `debt` | известный компромисс, зафиксирован осознанно |
| `docs` | расхождение документации и кода |

**Формулировка — наблюдаемым поведением.** Не «переписать svc_speed»,
а «скорость показывает втрое меньше реальной при 300 об/мин».

Каждая задача содержит: что наблюдается, что ожидается, как проверить.
Задачи со `safety` дополнительно — что происходит в худшем случае.

## 6. Коммиты и ветки

Один коммит — одно изменение. Не смешивать исправление с рефакторингом,
рефакторинг с новой функциональностью.

Формат сообщения:

```
<область>: <что изменилось в повелительном наклонении>

<зачем, если неочевидно>
<ссылка на issue / ADR>
```

Области: `hal`, `svc`, `app`, `cfg`, `util`, `web`, `tests`, `docs`, `ci`.

```
hal: вернуть проверку переполнения TX-буфера

Из serial_write была удалена проверка заполнения кольцевого буфера.
При телеметрии 41 байт в буфер 9 байт каждый пакет затирал сам себя.
Closes #3
```

Изменения, затрагивающие безопасность, содержат в теле строку
`Safety: <что именно меняется в поведении>`.

## 7. Тесты

- **Любое изменение в `util_*`, `cfg_*`, `svc_*` сопровождается тестом.**
  Эти модули платформонезависимы и собираются на десктопе через `g++`.
- **Исправление дефекта начинается с теста, который его воспроизводит.**
  Сначала красный, потом правка, потом зелёный. Тест остаётся навсегда.
- **Формулы проверяются эталонными точками** с вручную посчитанным
  ожидаемым значением, а не «результат выглядит правдоподобно».
- HAL проверяется на железе. Для сервисов пишутся моки HAL-функций
  в тестовом файле — пример в `tests/test_cfg_settings.c`.

```bash
cd tests && make run     # должно быть 0 failed
cd tests && make clean   # перед коммитом
```

## 8. Definition of Done

Задача закрыта, когда выполнено всё:

1. Критерий приёмки сформулирован **наблюдаемым поведением**.
   Плохо: «добавлен watchdog». Хорошо: «при зависании основного цикла
   контроллер перезагружается за 8 секунд, ШИМ обнуляется, проверено
   осциллографом».
2. Тест воспроизводил проблему и стал зелёным.
3. `make run` — 0 failed.
4. Затронутая документация обновлена **тем же изменением**.
5. Неочевидное решение записано как ADR.
6. Если задача была `hw-unknown` — результат замера внесён
   в `HARDWARE_BRINGUP.md`.

## 9. Что требует решения владельца

Ассистент предлагает, владелец решает. По этим темам не действовать
самостоятельно — оформить развилку таблицей «что делает / чем платим»,
дать рекомендацию, дождаться ответа:

- поведение педалей, тормоза, рампы, аварийной остановки;
- любой watchdog и любая политика при отказе;
- протокол и формат телеметрии;
- структура настроек и раскладка EEPROM;
- новые зависимости;
- частоты, таймеры, распиновка;
- всё, что меняет обещание, данное в `SPECIFICATION.md`.

## 10. Осмысленные состояния вместо заглушек

Если значение неизвестно — нет датчика, функция не реализована — это
**отдельное именованное состояние**, а не ноль и не среднее.

Запрещено:
- отвечать `ACK` на невыполненную команду;
- отдавать в телеметрии захардкоженное значение как измеренное;
- возвращать `0` там, где смысл «данных нет».

Требуется:
- `NACK` с кодом «не реализовано», и интерфейс это показывает;
- признак достоверности рядом со значением либо отдельный код;
- счётчик для каждого молчаливого отказа: переполнение буфера,
  пропуск дедлайна, отброшенный по CRC пакет.

Правило простое: **у любого отказа должно быть имя и счётчик.**
