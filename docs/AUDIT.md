# Технический аудит проекта EV Controller

**Дата:** 09.09.2026
**Объём:** firmware (37 файлов), web GUI (17 файлов), тесты (71), документация
**Метод:** чтение кода, проверка формул расчётами, сквозная сверка слоёв протокола, сверка с `Методология_разработки_v1.0.md`
**Статус проверки на железе:** прошивка не запускалась на реальном контроллере ни разу

---

## 0. Вердикт

**Структура — хорошая. Реализация — не поедет.**

Разделение на слои, изоляция платформы в одном файле, настройки в EEPROM с CRC, конфигурируемый комбинатор педалей, модульный фронтенд — это правильные решения уровня senior. Они не потребуют переписывания.

Но внутри этой структуры находятся дефекты, из-за которых система в текущем виде **не заработает при первом включении**, а три из них — вопросы безопасности ребёнка. Причина одна и та же: код писался «вперёд», без единого прогона на железе и без тестов на критических модулях. Всё, что покрыто тестами (`util_math`, `cfg_settings`, `svc_ramp`), — корректно. Всё, что не покрыто (`svc_speed`, `svc_pedals`, протокол, UART), — содержит дефекты.

Это ровно то, о чём говорит методология: **«держится сборкой, а не памятью»**. Здесь оно держалось памятью — и не удержалось.

## 1. Блокирующие дефекты

### B-1. TX-буфер UART в 9 байт вместо 64 — телеметрия физически не пролезает

`cfg_board.h` объявляет `TX_BUFFER_SIZE 64`. Но `MICRO_UART.cpp` **не включает `cfg_board.h`** — только собственный заголовок. В этой единице трансляции срабатывает `#ifndef` по умолчанию: `TX_BUFFER_SIZE = 8`, кольцевой буфер = 9 байт.

Пакет телеметрии — 36 байт данных + 5 служебных = **41 байт**.

Хуже: из `serial_write()` **удалена проверка переполнения**, которая есть в оригинальном Grbl:

```c
void serial_write(uint8_t data) {
  uint8_t next_head = serial_tx_buffer_head + 1;
  if (next_head == TX_RING_BUFFER) { next_head = 0; }

  /* ← здесь в Grbl стоит:
       while (next_head == serial_tx_buffer_tail) { ... }
     в этом коде — пустая строка */

  serial_tx_buffer[serial_tx_buffer_head] = data;   // затирает неотправленные данные
  serial_tx_buffer_head = next_head;
}
```

**Следствие:** каждый пакет телеметрии затирает сам себя в буфере. CRC не сойдётся, веб не получит ничего. Разработчик увидит «Arduino подключён, данных нет» и будет искать проблему в Python.

**Исправление:** добавить `#include "cfg_board.h"` первой строкой `MICRO_UART.cpp` **и** вернуть проверку заполнения. Вопрос политики при переполнении — отдельное решение: блокировать (как Grbl) нельзя в цикле управления 100 Гц; правильнее отбрасывать пакет целиком и считать счётчик потерь как перечислимый исход.

---

### B-2. Байт 0xFF в пакете уничтожает пакет

`SERIAL_NO_DATA = 0xFF` — сигнал «буфер пуст» из Grbl, где по UART шёл ASCII и 0xFF не встречался. В бинарном протоколе 0xFF — обычный байт данных.

```c
uint8_t byte = hal_uart_read();
if (byte == HAL_UART_NO_DATA) break;   // ← байт уже вынут из буфера и потерян
parser_feed(byte);
```

`serial_read()` **уже удалил байт** из кольцевого буфера, прежде чем вернуть его. Байт 0xFF молча исчезает, пакет рвётся, CRC не сходится.

Что ломается на практике:

| Команда | payload | Результат |
|---|---|---|
| `setGasVirtual(1023)` | `FF 03` | **никогда не доходит** |
| `setGasVirtual(767)` | `FF 02` | никогда не доходит |
| `setGasVirtual(511)` | `FF 01` | никогда не доходит |
| `setGasVirtual(255)` | `FF 00` | никогда не доходит |
| любая команда | CRC = `??FF` | теряется примерно 1 из 128 |

Полный газ по UART скомандовать невозможно. Остальные команды теряются случайно — самый неприятный класс отказов: «иногда работает».

**Исправление:** `hal_uart_read()` должен вернуть `int16_t` (−1 = пусто) либо читать через `hal_uart_available()` перед чтением. Сентинел внутри диапазона данных — архитектурная ошибка, а не мелочь.

---

### B-3. Расчёт скорости занижен в 3,6 раза

`svc_speed.cpp`:

```c
kmh_x10 = (avg_rpm * WHEEL_DIAMETER_MM * 188UL) / 360000UL;
```

Проверка при D = 200 мм, RPM = 300:

| | значение |
|---|---|
| Физика: `RPM·π·D·60/10⁶` | 11,31 км/ч → `kmh_x10 = 113` |
| Формула в коде | `31` → показывает 3,1 км/ч |

Правильно: `kmh_x10 = RPM · D · 1885 / 1000000`.

Отдельно стоит отметить комментарий над формулой — он содержит «проверку», которая подтверждает неверный результат:

```
(проверка: 3.1 км/ч × 200мм × π × 60 / 1000 = 3.14 км/ч ✓)
```

Это не арифметика, а совпадение с числом π. **Комментарий-самоподтверждение опаснее отсутствия комментария**: он выключает подозрение у следующего читателя. Именно поэтому методология требует эталонных фикстур, а не рассуждений в комментариях.

Дуга скорости на циферблате — центральный диагностический элемент всего дашборда (разница «скорость vs ШИМ» = нагрузка). Сейчас она врала бы втрое.

### B-4. Смена режима не работает, но интерфейс показывает, что работает

```c
static void handle_set_mode(...) {
    if (payload[0] >= DRIVE_MODE_COUNT) { send_nack(...); return; }
    /* TODO: интеграция с svc_drive_mode в MVP-3+ */
    send_ack(CMD_SET_MODE);     // ← ACK на невыполненную команду
}
```

`current_profile` присваивается один раз в `setup()` и больше не меняется. В телеметрии `t.drive_mode = DRIVE_MODE_ECO` захардкожен.

Родитель нажимает SPORT → кнопка подсвечивается, контроллер отвечает ACK, машина остаётся в ECO. Обратная ситуация опаснее: нажали ECO, чтобы ограничить ребёнка, — ограничение не применилось.

**Это нарушение принципа «система думает на глазах»** из методологии: интерфейс показывает не состояние системы, а собственное намерение. ACK на невыполненное действие — худший вариант: он гасит подозрение.

**Минимальное исправление до появления `svc_drive_mode`:** обновлять `current_profile` в обработчике и возвращать реальный режим в телеметрии. Либо честно отвечать `NACK(ERR_NOT_IMPLEMENTED)` — но тогда веб должен это показать.

## 2. Дефекты безопасности

### S-1. Аварийная остановка снимается сама через 200 мс

```c
handle_emergency_stop():
    svc_pedals_set_uart_gas(0);
    svc_pedals_set_uart_brake(1023);   // ставит uart_last_ms = now
```

и в `svc_pedals_update()` тот же watchdog применяется к обеим педалям:

```c
apply_watchdog(&gas,   now, timeout);   // 200 мс
apply_watchdog(&brake, now, timeout);   // 200 мс  ← и к тормозу тоже
```

Веб отправляет `emergencyStop()` **один раз** по нажатию. Через 200 мс `brake_uart` обнуляется. Если ребёнок держит педаль газа — машина поедет снова.

Ошибка в основе: **watchdog применён симметрично к асимметричным по безопасности величинам**. Обнуление газа при потере связи — безопасно (fail-safe). Обнуление тормоза — опасно (fail-dangerous). Один таймаут на оба.

**Исправление — два решения, оба нужны:**
1. Аварийная остановка должна **защёлкиваться** (latch) и сниматься только явной командой + подтверждением. Это отдельное состояние машины, а не «значение педали 1023».
2. Watchdog тормоза не должен обнулять тормоз. При потере связи корректное поведение — *удерживать* торможение, а не снимать.

По методологии это «необратимое/критичное действие с одной охраняемой дверью»: E-STOP — не педаль, а состояние.

---

### S-2. Аппаратный watchdog никогда не включается

ТЗ §8.3 требует: *«Watchdog Arduino: аппаратный, 8 сек»*.
`ARCHITECTURE.md` перечисляет `hal_system_wdt_reset` как задачу с приоритетом «Критический», интервал 10 мс.

В коде: `hal_system_wdt_enable()` реализован в HAL и **не вызывается ниоткуда**. `wdt_reset()` в планировщик не добавлен.

Зависание прошивки при поданном ШИМ = машина едет без управления до разряда батареи или физического E-Stop.

Отдельно: включение watchdog требует аккуратности со старыми загрузчиками Arduino Nano (после сброса по watchdog устройство может уйти в бесконечный ребут). Это надо решать вместе с выбором загрузчика, а не «дописать строчку».

---

### S-3. Настройки принимают любые значения и уходят в EEPROM

```c
uint8_t cfg_settings_set_field(uint16_t offset, const void *data, uint8_t size)
{
    if (offset + size > sizeof(settings_t)) return 1;   // единственная проверка
    memcpy(ptr + offset, data, size);
    return 0;
}
```

Проверяется только выход за границы структуры. Не проверяется ничего по смыслу:

| Запись | Последствие |
|---|---|
| `brake_rate_max = 0` | **тормоз перестаёт работать**, сохраняется в EEPROM |
| `brake_rate_min = 0` | то же при слабом нажатии |
| `max_pwm = 65535` | выход за диапазон, спасает только клэмп ниже по цепочке |
| `motor_deadzone = 200` | резкий старт с 20 % ШИМ |
| `uart_pedal_timeout_ms = 65535` | watchdog виртуальных педалей отключён |
| `gas_combinator = 4` (UART_ONLY) | физическая педаль ребёнка перестаёт действовать |

Смещения приходят из веба «как есть». Ошибка в схеме на фронтенде (сдвиг на два байта при добавлении поля в `settings_t`) тихо запишет мусор в соседнее поле и **сохранит его в EEPROM**.

Это прямое нарушение принципа **«единственный писатель»** и **«опасные способности — за шлюзом»**: у настроек нет валидатора, нет одной охраняемой двери.

**Исправление:** таблица дескрипторов полей (offset, размер, min, max, «требует остановки»), разделяемая между прошивкой и вебом. Запись только через идентификатор параметра, а не сырое смещение. Это же снимет проблему рассинхронизации схемы.

---

### S-4. Нулевой ШИМ в режиме Fast PWM даёт импульсы

В Phase-Correct при `OCR = 0` выход постоянно в нуле — корректно. В Fast PWM при `OCR = 0` на выходе остаётся импульс шириной один такт каждый период (особенность ATmega328P). Профиль `SPORT` в дефолтах настроен на 15625 Гц; при переходе на Fast PWM «ноль» перестанет быть нулём.

Для контроллера мотора свойство «ШИМ = 0 означает выключено» должно быть гарантией, а не следствием выбранного режима. Сейчас оно не проверяется ни тестом, ни кодом.

## 3. Точность управления

### T-1. Планировщик даёт систематический сдвиг, а рампа этого не знает

```c
uint32_t elapsed = now - tasks[i].last_run_ms;
if (elapsed >= tasks[i].interval_ms) {
    tasks[i].last_run_ms = now;      // ← не += interval_ms
    tasks[i].func();
}
```

`last_run_ms = now` вместо `+= interval_ms` означает: период всегда **не меньше** заданного и накапливает остаток. При интервале 10 мс и джиттере цикла реальная частота будет 90–99 Гц, а не 100.

При этом `svc_ramp` инициализируется числом `100` и считает, что вызывается ровно 100 раз в секунду:

```c
svc_ramp_init(CONTROL_FREQ_HZ);   // аккумулятор делит на 100
```

Значит `accel_rate = 200 PWM/сек` на самом деле даст 180–198 PWM/сек. Красивая целочисленная арифметика аккумулятора в `util_math` (которая протестирована и корректна) обеспечивает точность, которую система всё равно не выдерживает — потому что нижележащее допущение о постоянстве шага неверно.

То же касается `svc_speed_update(SPEED_FREQ_HZ)` — RPM считается из предположения, что прошло ровно 100 мс.

**Два варианта решения, выбор архитектурный:**
- `last_run_ms += interval_ms` с ограничением догона — сохраняет среднюю частоту, но при перегрузке даёт пачку вызовов подряд;
- передавать в сервисы фактический `dt` — честнее, устойчивее к джиттеру, но меняет сигнатуры `svc_ramp_update` и `svc_speed_update`.

Для транспортного средства я бы выбрал второй: скорость нарастания ШИМ — параметр безопасности, он не должен зависеть от загрузки процессора.

Дополнительно: **пропуск дедлайна ничем не фиксируется**. Нет ни счётчика, ни флага. Методология: *«перечислимые исходы вместо молчаливых пустот»* — просроченный тик критической задачи это исход, у него должно быть имя и счётчик в телеметрии.

### T-2. Аккумулятор рампы общий для разгона, торможения и оттормаживания

`apply_step()` использует один `accum` для трёх разных скоростей. При переключении «разгон → торможение» дробный остаток от предыдущей скорости переносится в новый режим. Величина эффекта мала (< 1 единица ШИМ), но это скрытая связанность: три независимых процесса делят одно состояние.

## 4. Полнота протокола

Сквозная проверка трёх слоёв показала расхождения:

| Команда | `app_protocol.h` | обработчик в прошивке | `server.py` | `protocol.js` |
|---|---|---|---|---|
| `SET_TELEM_RATE` | объявлена | **отсутствует** | есть в payload-builder | вызывается |
| `GET_TELEMETRY` | объявлена | **отвечает ACK, телеметрию не шлёт** | есть | есть |
| `GET_PARAM` / чтение настроек | **не существует** | — | — | — |

Первые две — мёртвые пути: JS может отправить команду, которая гарантированно вернёт NACK.

Третья важнее. **Прочитать настройки из контроллера нечем.** Следующая запланированная задача — вкладка Settings — требует «прочитать текущие значения → показать форму → записать изменённые». Первый шаг невозможен без новой команды и, вероятно, нового формата ответа (182 байта не влезают в один пакет с текущим `PROTO_MAX_PAYLOAD = 60` — нужна пагинация или чтение по полям).

Это ровно та находка, которую методология ловит **на бумаге**: раздел «Карта API: сценарии → команды и события» существует именно для того, чтобы экран, которому не хватает команды, вскрылся до написания кода.

Прочее по протоколу:
- нет номеров пакетов и сопоставления ACK с запросом — на RS485 рядом с моторами это понадобится;
- нет версии протокола в пакете — при обновлении прошивки старый веб будет молча неправильно разбирать телеметрию;
- `RSP_NACK` не имеет кода «не реализовано»;
- сохранение в EEPROM (`CMD_SAVE_SETTINGS`) не ограничено по частоте — веб может исчерпать ресурс ячеек (100 тыс. циклов).

## 5. Веб-часть

Структура правильная: `transport` / `protocol` / `store` / изолированные виджеты. Замена транспорта на ESP32 действительно потребует правки одного файла. Это решение окупится.

Дефекты:

**W-1. Графики пишут точку на любое изменение состояния.**
```js
store.subscribe((s) => this._push(s));   // charts.js
```
`store.appendLog()` тоже вызывает `_notify()`. Любое отладочное сообщение от контроллера добавляет лишнюю точку на все три графика. Ось времени перестаёт быть равномерной — а именно по ней предполагается сравнивать реакцию системы на нажатие педали. Нужна подписка на конкретный срез (телеметрию), а не на весь store.

**W-2. Счётчик «RX rate» считает уведомления store, а не пакеты** — по той же причине завышен.

**W-3. Нет авторизации и подтверждения происхождения команд.** Сейчас сервер слушает `localhost` — приемлемо. Но `--ws-host 0.0.0.0` открывает управление транспортным средством в сеть без единой проверки. Для ESP32 (ТЗ §3.3 требует пароль и защиту от несанкционированного запуска) это придётся проектировать заново. Лучше заложить границу доверия сейчас, чем встраивать её в готовый интерфейс.

**W-4. `ev_control.py` использует протокол v1** (`CMD_SET_SPEED`), которого в прошивке больше нет. Утилита нерабочая, но лежит в репозитории и упоминается в README как рабочая.

## 6. Сверка с методологией

Документ «Методология разработки v1.0» — сильный и применимый здесь почти целиком. Ниже — где проект ему соответствует и где нет.

| Принцип | Состояние |
|---|---|
| **Ядро отделено от интерфейса** | ✅ Соблюдён. Прошивка не знает про веб, веб — про Serial. |
| **Единственный писатель** | ❌ Нарушен для настроек: писать может любой пакет по сырому смещению, без валидатора. |
| **Расширяемость через контракты** | ⚠️ Частично. Слои разделены, но контракт «настройки» описан только структурой C, без схемы, разделяемой с клиентом. |
| **Опасные способности — за шлюзом** | ❌ Нет шлюза ни у настроек, ни у команд движения. |
| **Перечислимые исходы вместо молчаливых пустот** | ❌ Пропуск дедлайна, переполнение TX, потерянный байт 0xFF, невыполненная смена режима — всё молча. |
| **Осмысленные состояния вместо заглушек** | ❌ `drive_mode` захардкожен, `faults` всегда 0, токи всегда 0 — заглушки выдаются за данные. |
| **Система думает на глазах** | ❌ Интерфейс показывает намерение, а не состояние (режим, E-STOP). |
| **Держится сборкой, а не памятью** | ❌ CI нет. Правило «в сервисах нет Arduino.h» соблюдается (проверил), но ничем не закреплено. |
| **Property-тесты инвариантов там, где цена ошибки — данные/безопасность** | ❌ Протестировано ровно то, что и так корректно. Комбинатор педалей — модуль, решающий, поедет ли машина, — не покрыт ни одним тестом. |
| **Эталонные фикстуры** | ❌ Формула скорости не имеет ни одной проверочной точки; ошибка в 3,6 раза жила в комментарии-«проверке». |
| **ADR-культура** | ❌ Решений принято много (комбинатор педалей, слоистая модель, 4 слоя, бинарный протокол, vanilla JS), ни одно не записано как ADR с отклонёнными альтернативами. |
| **Definition of Done наблюдаемым поведением** | ❌ «Готово» означало «код написан». Ни один MVP не имеет критерия приёмки, который можно показать. |
| **Доверие ступенями (read-only → планы → действия с откатом)** | ❌ Пропущено. Первая же версия веб-интерфейса умеет двигать машину. Разумнее было начать с режима наблюдения. |

Самое ценное, что даёт методология этому проекту, — **порядок фаз**. Здесь фактически прыгнули из ТЗ сразу в архитектуру и код, пропустив «сценарии по экранам» и «карту API». Обе пропущенные фазы вскрыли бы дефекты B-4 (режим), раздел 4 (нет чтения настроек) и S-1 (E-STOP как состояние, а не значение) **на бумаге, за час**.

## 7. Что в проекте сделано хорошо

Это не формальность — перечисленное ниже не надо трогать при исправлениях.

- **Изоляция платформы в одном файле** — сделана честно. Проверено: ни один сервисный модуль не включает `Arduino.h` или `avr/io.h`. Портирование на STM32 действительно сведётся к замене `hal_atmega328p.cpp`.
- **Настройки в EEPROM с magic + version + CRC16** и корректным откатом к дефолтам при повреждении. Проверено тестом с порчей байта.
- **Слоистая модель педалей с настраиваемым комбинатором** — сильное продуктовое решение. Оно точно описывает реальный сценарий («родитель подтормаживает, отпускает, ребёнок едет дальше») и делает его настраиваемым без перепрошивки. Это лучшая идея в проекте.
- **Целочисленная арифметика везде**, аккумулятор рампы с точной средней скоростью, PID с anti-windup — реализовано корректно и покрыто тестами.
- **Модульность фронтенда** с абстрактным транспортом — окупится при переходе на ESP32.
- **Документация** — подробная и структурированная. Проблема не в её отсутствии, а в том, что она местами описывает намерение как факт (watchdog в таблице задач, «не используем digitalWrite» при том, что HAL им и реализован).

## 8. План исправлений

### Очередь 0 — до любого включения на столе
Без этого проверять нечего.

1. `MICRO_UART.cpp`: включить `cfg_board.h`, вернуть проверку переполнения TX, добавить счётчик отброшенных байт.
2. Убрать сентинел 0xFF: `hal_uart_read()` → `int16_t` или чтение через `available()`.
3. Исправить формулу `kmh_x10`, добавить тест с тремя эталонными точками.
4. Включить аппаратный watchdog + `wdt_reset()` в планировщике (с проверкой поведения загрузчика).

### Очередь 1 — до первого запуска с мотором
5. E-STOP как защёлкивающееся состояние, снимаемое явной командой.
6. Watchdog тормоза не обнуляет тормоз (асимметрия fail-safe).
7. Валидатор настроек: таблица дескрипторов полей с диапазонами; запись по идентификатору, не по смещению.
8. Смена режима: либо реально работает, либо честный NACK и веб это показывает.

### Очередь 2 — до расширения функциональности
9. Решить вопрос `dt`: фактическое время шага в `svc_ramp` и `svc_speed`; счётчик пропущенных дедлайнов в телеметрии.
10. Команды чтения настроек + версия протокола в пакете.
11. Тесты на `svc_pedals` (все пять комбинаторов, watchdog, приоритет тормоза), `svc_speed` (эталонные точки), парсер протокола (битый CRC, обрыв пакета, мусор перед SYNC, байт 0xFF в payload).
12. CI-сторож: «в `svc_*`/`util_*`/`cfg_*` нет `Arduino.h`/`avr/`», сборка тестов, прогон.

### Очередь 3 — процесс
13. Завести `docs/adr/`, записать задним числом принятые решения с альтернативами.
14. Написать пропущенные документы: сценарии по экранам и карту API (§1 методологии). Это займёт день и закроет вопрос «чего ещё не хватает в протоколе».
15. Definition of Done для каждого MVP — наблюдаемым поведением.

## 9. Незакрытые вопросы к владельцу

1. **`ENCODER_PULSES_PER_REV` и `WHEEL_DIAMETER_MM`** — сейчас 12 и 200 мм, оба выдуманы. Пока они неизвестны, скорость и одометр не имеют смысла. Замер: прокрутить колесо ровно на оборот, посчитать импульсы.
2. **Скорость UART** — 9600 бод. Телеметрия 41 байт × 10 Гц занимает 43 % канала, отладочный текст в том же порту — ещё часть. ТЗ §7.1 закладывает 115200. Разумно перейти сейчас: это снимет борьбу за буферы.
3. **Отладочный текст и бинарный протокол в одном порту** — работает случайно (ASCII не содержит 0xAA). Оставляем как есть или разводим по признаку сборки?
4. **Поведение при переполнении TX** — отбрасывать пакет целиком, блокировать, или снижать частоту телеметрии автоматически?
5. **Загрузчик Nano** — старый или новый? От этого зависит, безопасно ли включать watchdog.
6. **Что должно происходить при потере связи с вебом** во время активного UART-газа: плавное снятие газа (сейчас) или ещё и подтормаживание?

## 10. Итог

Проект не нужно начинать заново. Скелет выдержит и MVP-2, и MVP-3.

Но нужно принять, что **текущий код — это черновик, который никогда не исполнялся**, и относиться к нему соответственно: не «допилить фичи», а сначала довести до состояния «включается и не врёт», закрыв очереди 0 и 1.

Главный системный вывод: в проекте отсутствует механизм, который ловит расхождение между тем, что написано в документации, и тем, что делает код. Watchdog в таблице задач, но не в коде. Буфер 64 в конфиге, но 8 в сборке. Режим в интерфейсе, но не в контроллере. Скорость с формулой и «проверкой», но в 3,6 раза мимо.

Методология называет это одним предложением, и оно должно стать правилом проекта:

> **Держится сборкой, а не памятью.**
