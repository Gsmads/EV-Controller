# Протокол управления UART/RS485

**Версия:** 3.0.0
**Скорость:** 250000 бод (ADR-0015), по ADR-0019 станет настройкой с откатом
**Истина:** `firmware/app_protocol.h`. Этот документ обязан ей соответствовать.

---

## Формат кадра

```
[ COBS( CMD | PAYLOAD... | CRC16_L | CRC16_H ) ] [ 0x00 ]
```

| Часть | Размер | Описание |
|---|---|---|
| CMD | 1 | Идентификатор команды |
| PAYLOAD | 0..60 | Данные команды |
| CRC16 | 2 | CRC16-CCITT по `CMD + PAYLOAD`, little-endian |
| `0x00` | 1 | Разделитель кадров |

Байта синхронизации и поля длины **нет**. Длина кадра следует из положения
разделителей.

Размеры: пакет до кодирования не больше 63 байт, кодирование добавляет ровно
один байт, разделитель ещё один — **максимум 65 байт в линии**.

### Почему COBS

Consistent Overhead Byte Stuffing убирает байт `0x00` из данных. Поэтому
`0x00` можно использовать как границу кадра, и эта граница **не может
встретиться внутри кадра ни при каких данных**.

Прежний формат (v2) искал начало кадра по байту `0xAA` и брал длину из поля
`LEN`. Оба поля — обычные данные: `0xAA` встречается в полезной нагрузке
свободно, а испорченный `LEN` заставлял приёмник съесть до 61 чужого байта.
Отсюда дефект T-4: повреждение одного байта уносило соседний кадр.

Подробности и отклонённые варианты — [ADR-0024](adr/0024-obramlenie-kadra-cobs.md).

### Что гарантирует обрамление, а что нет

| Случай | Что происходит |
|---|---|
| Повреждён байт внутри кадра | Теряется только этот кадр. Следующий разбирается сразу |
| Ложное начало кадра | Невозможно: разделителя внутри кадра не бывает |
| Помеха между кадрами | Закрывается ближайшим разделителем, кадры не затрагивает |
| **Оборвалась передача, разделитель не ушёл** | Обрывок склеивается со следующим кадром, и тот теряется. Восстановление ровно через один кадр, не позже |

Последний случай — честная граница возможностей: сказать, что кадр кончился,
нечему, если сигнал об этом не был передан. Закрывается межкадровым таймаутом
поверх COBS; такое решение не принято.

### Кодирование COBS в двух словах

Вход делится на группы, разделённые нулями. Каждой группе предшествует
байт-код — расстояние до следующего нуля. Код `0xFF` означает группу из 254
ненулевых байт, за которой нуля нет.

```
{}                  -> 01
{00}                -> 01 01
{11 22}             -> 03 11 22
{11 00 22}          -> 02 11 02 22
```

Эталонные реализации: `firmware/util_cobs.cpp` и `cobs_encode`/`cobs_decode`
в `tools/gui/server.py`. Они сверены между собой на 256 векторах.

### Отладочный текст в том же порту

Прошивка пишет в тот же UART человекочитаемую отладку. Чтобы текст и кадры
не склеивались, каждая строка отладки завершается тем же байтом `0x00`
(`app_debug.cpp`). Правило разбора получается одно на всё:

1. копить байты до `0x00`;
2. попробовать раскодировать накопленное как кадр и проверить CRC;
3. не вышло, но байты печатные — показать как текст.

В ASCII нуля нет, поэтому внутри строки разделитель встретиться не может.

## Команды Host → Controller

| CMD | Имя | Payload | Описание |
|---|---|---|---|
| 0x01 | `SET_GAS_VIRTUAL` | uint16 LE | Виртуальный газ 0–1023 |
| 0x02 | `SET_BRAKE_VIRTUAL` | uint16 LE | Виртуальный тормоз 0–1023 |
| 0x03 | `SET_MODE` | uint8 | Режим вождения (`drive_mode_id_t`) |
| 0x04 | `EMERGENCY_STOP` | — | Мягкая аварийная остановка |
| 0x05 | `RELEASE_CTRL` | — | Сбросить обе виртуальные педали в 0 |
| 0x10 | `SET_PARAM` | uint16 offset + uint8 size + данные | Запись поля настроек |
| 0x11 | `SAVE_SETTINGS` | — | Сохранить настройки в EEPROM |
| 0x12 | `RESET_DEFAULTS` | — | Сброс к заводским |
| 0x13 | `RESET_ODOMETER` | — | Сброс одометра |
| 0x20 | `GET_TELEMETRY` | — | Запрос одного пакета телеметрии |
| 0x21 | `SET_TELEM_RATE` | uint8 | Частота автотелеметрии (0 = выкл, 1–50 Гц) |
| 0xFE | `PING` | — | Проверка связи |

### Модель управления: слоистые педали

`svc_pedals` хранит **отдельно** физическую педаль (АЦП) и виртуальную (UART).
Комбинатор (`gas_combinator` / `brake_combinator` в настройках) объединяет их;
по умолчанию `MAX` — родитель может «доложить» поверх ребёнка, но не отнять.
Пять комбинаторов разобраны в [ADR-0004](adr/0004-sloistaya-model-pedalej.md).

Watchdog виртуальных педалей: если команда не приходит `uart_pedal_timeout_ms`
(по умолчанию 200 мс), виртуальная педаль сама сбрасывается в 0.

## Ответы Controller → Host

| CMD | Имя | Payload | Описание |
|---|---|---|---|
| 0x80 | `RSP_ACK` | uint8 cmd | Команда выполнена |
| 0x81 | `RSP_NACK` | uint8 cmd + uint8 err | Отказ с кодом |
| 0x82 | `RSP_TELEMETRY` | 36 байт | Пакет телеметрии |
| 0x83 | `RSP_PONG` | — | Ответ на `PING` |

### Коды отказа

| Код | Имя | Когда |
|---|---|---|
| 0x01 | `ERR_UNKNOWN_CMD` | Команда не известна |
| 0x02 | `ERR_BAD_PAYLOAD` | Длина данных не та, что нужна команде |
| 0x03 | `ERR_BAD_MODE` | Номер режима вне диапазона |
| 0x04 | `ERR_PARAM_RANGE` | Значение параметра отвергнуто реестром |

Реестр параметров различает больше причин отказа (`PARAM_UNKNOWN`,
`PARAM_SIZE_MISMATCH`, `PARAM_READONLY`, `PARAM_OUT_OF_RANGE`,
`PARAM_OUT_OF_BOUNDS`), но на проводе они пока сводятся к `ERR_PARAM_RANGE`.
Развести их — правка протокола, она не сделана.

## Структура телеметрии (36 байт)

Порядок полей обязан совпадать с `telemetry_packet_t` в `app_protocol.h`
и с `struct.unpack` в `server.py`. Все многобайтовые поля little-endian.

| Смещение | Тип | Поле | Описание |
|---|---|---|---|
| 0 | uint16 | `gas_physical` | Физическая педаль газа, 0–1023 |
| 2 | uint16 | `gas_uart` | Виртуальный газ, 0–1023 |
| 4 | uint16 | `gas_effective` | После комбинатора, 0–1023 |
| 6 | uint16 | `brake_physical` | Физический тормоз |
| 8 | uint16 | `brake_uart` | Виртуальный тормоз |
| 10 | uint16 | `brake_effective` | После комбинатора |
| 12 | uint16 | `target_pwm` | Целевой ШИМ, 0–1023 |
| 14 | uint16 | `current_pwm` | Текущий ШИМ после рампы |
| 16 | uint16 | `pwm_freq_hz` | Частота ШИМ |
| 18 | uint16 | `speed_rpm_l` | Обороты левого колеса |
| 20 | uint16 | `speed_rpm_r` | Обороты правого колеса |
| 22 | uint16 | `speed_kmh_x10` | км/ч × 10 |
| 24 | uint16 | `current_ma_l` | Ток левого мотора, мА |
| 26 | uint16 | `current_ma_r` | Ток правого мотора, мА |
| 28 | uint8 | `drive_mode` | Режим вождения |
| 29 | uint8 | `uart_active_flags` | бит 0: `gas_uart > 0`, бит 1: `brake_uart > 0` |
| 30 | uint16 | `faults` | Битовое поле ошибок |
| 32 | uint32 | `uptime_ms` | Время работы |

### Чего в телеметрии ещё нет

Эти величины считаются в прошивке, но наружу не выведены — добавление полей
меняет размер пакета и делается одной ревизией:

- `uart_tx_dropped` — отброшенные при переполнении кадры (ADR-0016);
- `uart_baud_reverts` — откаты скорости порта (ADR-0019);
- `app_protocol_bad_frames()` — кадры, не прошедшие разбор;
- `hal_encoder_glitch_count()` — отброшенные фильтром дребезга фронты;
- состояние скорости (`SPEED_NO_DATA` / `STOPPED` / `MOVING`, ADR-0023).

Поля `drive_mode`, `faults`, `current_ma_l/r` сейчас отдают заглушки, а не
измерения. Это записано в `AUDIT.md` (B-4) и должно быть либо реализовано,
либо честно помечено как «нет данных».

## Приоритет управления

1. **Тормоз главнее газа.** Любое ненулевое нажатие тормоза делает целевой
   ШИМ нулём — и физическое, и по UART.
2. **Комбинатор решает остальное.** По умолчанию `MAX`: действует больший из
   двух входов.
3. **Watchdog не спрашивает.** Молчание по UART дольше таймаута — виртуальные
   педали в ноль, без команды и без ответа.

## Веб-утилита

```bash
cd tools/gui
pip install -r requirements.txt
python server.py            # http://localhost:8000
```

`server.py` держит последовательный порт и раздаёт браузеру JSON по вебсокету.
Браузер о двоичном формате не знает — сборка и разбор кадров целиком в
`server.py`.
