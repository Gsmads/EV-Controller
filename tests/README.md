# EV Controller — Desktop Unit Tests

Десктопные юнит-тесты, проверяющие платформонезависимые модули прошивки
на компьютере **без подключения Arduino**.

Это позволяет:
- быстро прогонять регрессионные тесты после каждого изменения;
- ловить ошибки логики до загрузки в железо;
- работать над математикой и алгоритмами на ПК.

## Запуск

```bash
make run         # Собрать и запустить все тесты
```

Или по отдельности:

```bash
make             # Собрать все
./test_util_math
./test_cfg_settings
./test_svc_ramp

make clean       # Удалить бинарники
make verbose     # Пересобрать с дополнительными предупреждениями
```

**Требования:** только `g++` (любая версия с поддержкой C++11). Никаких внешних
библиотек, фреймворков, CMake.

## Что покрыто (314 тестов)

### test_util_math.c — 33 теста

Модуль математических утилит:
- `map / clamp` — линейное масштабирование и ограничение
- `EMA-фильтр` — сходимость, реакция на скачок
- **Кривые отклика педали** — linear, quadratic, s-curve (все три)
- **PID-регулятор** — pure P, P+I с накоплением, pure D, anti-windup, reset
- **Аккумулятор рампы** — точные дробные приращения (rate=150 ≠ 0!)

### test_util_ring.c — 48 тестов

Кольцевой буфер UART (ADR-0018), переносимая часть драйвера:
- запись, чтение, порядок FIFO, обёртывание индексов, сброс
- **B-1** — запись в полное кольцо отвергается и не затирает
  ранее записанные байты
- **B-2** — байт `0xFF` читается как данные: признак «пусто» это `-1`,
  а не значение, представимое в данных
- **ADR-0016** — блок пишется целиком либо не пишется вовсе,
  счётчик отвергнутых блоков растёт ровно на единицу
- все 256 значений байта проходят без искажения

### test_app_protocol.c — 20 тестов

Парсер бинарного протокола — единственная дверь для команд извне:
- мусор перед синхробайтом, битый CRC, оборванный кадр, длина 0 и длина
  сверх допустимой
- **байт `0xFF` в данных**: команда «полный газ» (1023 = `FF 03`) доходит.
  Раньше не доходила никогда — дефект B-2
- связка с реестром: попытка обнулить тормоз через протокол получает NACK
- **найден дефект T-4**: оборванный кадр съедает начало следующего

### test_cfg_params.c — 37 тестов

Реестр параметров, дефект S-3 — одна охраняемая дверь для записи настроек:
- **`brake_rate_max = 0` отвергнут** во всех девяти профилях: это
  отключение тормоза, и прежний код его записывал
- `pedal_ema_alpha = 0` отвергнут — фильтр остановился бы навсегда
- границы из устройства системы: АЦП 0…1023, кривых три, каналов восемь,
  датчик тока до 20 А
- запись в середину поля, несовпадение размера, байты выравнивания
- сентинел `0xFF` в профиле («брать общую кривую») допустим, а 3 — нет

### test_svc_pedals.c — 54 теста

Слоистая модель педалей и работа с сигналами (ADR-0020):
- **сервис читает сигналы по имени** и ни разу не обращается к каналу
  по номеру — мок считает обращения обоих видов
- чужие сигналы (токи, руль) не трогаются
- физическая педаль, виртуальная по UART
- watchdog виртуальной педали: команды кончились — педаль отпущена
- **все пять комбинаторов**, по тесту на каждый (ADR-0004):
  `MAX` берёт больший из двух входов, `ADDITIVE_CLAMP` складывает и
  упирается в потолок 1023, а не переполняется, `UART_PRIORITY` отдаёт
  управление ненулевой команде и возвращает педали при нулевой,
  `PHYSICAL_ONLY` и `UART_ONLY` глухи ко второму входу
- неизвестный номер комбинатора не отключает педаль, а работает как `MAX`
- при `PHYSICAL_ONLY` команда по UART всё равно видна в телеметрии —
  игнорируется она не молча
- **три кривые отклика по эталонным точкам**: сырое 273 даёт четверть
  хода (256), и на ней linear возвращает 256, quadratic 64 = 256²/1023,
  s-кривая 160 = (3t²−2t³)·1023 при t = 0,25; середина хода —
  неподвижная точка s-кривой
- мёртвая зона: 30 — ещё ноль, 31 — уже единица, а верх хода растянут
  обратно на весь диапазон
- `svc_pedals_get_target_pwm()`: масштаб по `max_pwm`, приоритет тормоза
  над газом, порог страгивания мотора как нижняя граница (но не для нуля)
- **дефект T-7**: кривая из профиля не действует, отклик берётся только
  из глобальных настроек
- **дефект T-6**: педаль в верхнем упоре даёт 1020 из 1023 — остаток
  сходимости фильтра. Тот же вход с точным засевом даёт 1023

### test_svc_speed.c — 18 тестов

Расчёт скорости (дефект B-3):
- **эталонные точки от физики** — RPM 50, 300, 600, 1200 при D = 200 мм
- прежняя формула на 300 RPM давала 31 вместо 113 — занижение в 3,65 раза
- линейность: удвоение оборотов удваивает скорость
- одометр, признак остановки, защита от нулевой частоты

### test_cfg_settings.c — 65 тестов

Менеджер настроек EEPROM:
- Загрузка defaults при пустом EEPROM
- Save → reload — сохранение и восстановление
- **CRC corruption** — повреждение байта → автоматический fallback к defaults
- Reset to defaults
- **Drive profiles** — Eco, Sport, Reverse, Failsafe — все параметры
- `set_field` — изменение по offset с проверкой границ
- Размер структуры — должен помещаться в 1 КБ EEPROM

Использует **mock EEPROM** (массив в RAM) вместо реального HAL.

### test_svc_ramp.cpp — 39 тестов

Сервис рампы с профилями режимов:
- Eco accel: 200 PWM/сек точно за 1 секунду
- Sport accel: 800 PWM/сек
- **Переключение профиля на ходу** — Eco → Sport
- Reset
- **аккумулятор дробных шагов**: 50 PWM/с при 100 Гц — это полшага за тик,
  и рампа обязана тронуться на втором тике, а не стоять вечно;
  250 PWM/с даёт 2,5 шага за тик и ровно 250 за секунду без дрейфа
- **интерполяция скорости торможения** по силе нажатия, с эталонными
  точками: нажатие 512 в Eco даёт 300 + 1200·512/1023 = 900/с = 9 ед/тик,
  и с 300 единиц это 34 тика; в пол — 20 тиков; касание — 100 тиков
- **дефект S-5**: касание тормоза (100 тиков) останавливает медленнее,
  чем просто отпущенный газ (75 тиков). Тест утверждает то, что есть
- тормоз главнее газа: при газе 1023 и тормозе 1023 ШИМ идёт вниз
- рампа **не применяет `max_pwm`** — это делает `svc_pedals_get_target_pwm()`
  до неё; тест защищает границу от «починки» не в том слое
- профиль Failsafe: `accel_rate = 0` означает, что за 10 секунд полного
  газа не будет сделано ни одного шага
- `svc_ramp_is_at_target()` во всех трёх состояниях

## Что НЕ покрыто

- **HAL** — тестируется на железе (требует MCU)
- **hal_atmega328p** — единственный платформенный модуль, проверяется только на железе
- **svc_motor** — тонкая обёртка над `hal_pwm`, проверяется на железе
- **связка кривой с профилем** — её нет в коде вообще (дефект T-7),
  тест фиксирует именно отсутствие
- **svc_motor** — требует mock_hal_pwm (TODO)

## Архитектура тестирования

```
┌──────────────────────────────────────────────────────┐
│  Десктоп (g++)                                       │
│                                                       │
│  ┌─────────────┐    ┌───────────────────────────┐  │
│  │  test_*.c   │───→│  Платформонезависимый код │  │
│  │             │    │  из ../firmware/          │  │
│  └─────────────┘    │  (util_*, svc_*, cfg_*)   │  │
│                     └───────────────────────────┘  │
│                                                       │
│  Mock HAL (in-memory EEPROM, фиктивные регистры)    │
└──────────────────────────────────────────────────────┘
```

Тесты включают `../firmware/<module>.h` и компилируют `../firmware/<module>.cpp`
напрямую. Mock HAL функций (например, `hal_nvm_*`) определены в тестовом
файле и переопределяют реальные при линковке.

## Добавление новых тестов

1. Создать `test_<module>.cpp` рядом с существующими
2. Использовать макросы `ASSERT_EQ`, `ASSERT_TRUE`, `ASSERT_RANGE` (определены в тестах)
3. Добавить правило в `Makefile`:
   ```makefile
   test_<module>: test_<module>.cpp $(FW)/<module>.cpp
       $(CXX) $(CXXFLAGS) -I$(FW) -o $@ $^
   ```
4. Добавить в список `TESTS := ...`

## CI

Эти тесты подходят для GitHub Actions / GitLab CI:

```yaml
- run: cd tests && make run
```

Выход 0 при успехе, 1 при любых упавших тестах.
